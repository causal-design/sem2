# SEM2 v0.1 implementation plan

Review draft. Build a small, usable package for fitting structural equation models and asking causal questions under a supplied graph. v0.1 should support the four model/example families below through consistent interfaces, with tests and documentation that make their assumptions clear.

This is the target scope, not a claim about what already works. The [55-item decision record](../meetings/2026-09-03-and-07/product-and-implementation-plan-updated.md) provides the meeting evidence, later Slack clarifications, and deferred work. [PROJECT.md](../../PROJECT.md) records implementation status.

## Supported models and example-level acceptance

| Model/example family | What v0.1 must demonstrate |
|---|---|
| Linear Gaussian SEM | Fit linear models, including a measurement-model example; check coefficients and moments against known values and use appropriate OLS/lavaan comparisons. |
| Discrete IV | Fit small finite-discrete instrumental-variable models, including binary and non-binary cases. Check finite-state probabilities and compare numerical partial-identification bounds with independently computed linear-programming bounds under the same assumptions. |
| Basic confounder adjustment | Fit a simulated model using the continuous energy-loss route and estimate a causal contrast whose value is known from the simulation. |
| Two-stage sequential randomized experiment | Represent two treatment stages and intermediate information potentially confounded with the outcome. Evaluate named joint interventions and check the chosen causal contrast against simulation truth. |

Use a small CPU-run collection, not a large simulation grid. Humans select the reference cases and numerical tolerances. These examples cover F15/F16/F25/F32/F34/F35/F40/F44 in the decision record.

## User workflow and data handling

- For ordinary fitting, specify the model and named data, choose the objective, fit, and inspect loss/gradient history. Then sample or evaluate named treatment/outcome queries without refitting solely to change the query.
- For partial identification, specify the target before query-specific optimization and investigate lower and upper values. An initial ordinary fit is optional; warm-start policy remains a design question. Numerical extrema are not automatically sharp bounds or confidence intervals.

Keep minimal column-to-node mapping and dataset-relative observed/latent status in v0.1. Implement the richer dataset schema in v0.2 (F02/F03).

Retain both finite-discrete fitting through `SEM2Discrete` and deliberate numeric treatment through base `SEM2`. Provide an explicit categorical-to-numeric conversion helper, analogous in purpose to R's `as.numeric` (F28). The chosen numeric representation is a modeling decision, not equivalent to finite-discrete fitting. Review the helper's name, placement, and conversion rules; do not expand it into the general preprocessing framework deferred under F09.

## Package changes and unit tests

Reuse the existing formula construction through `FormulaParser` and the model classes below. The names identify current implementation starting points, not approved new signatures. Keep changes local rather than introducing a new class hierarchy.

| Component | Work needed for v0.1 |
|---|---|
| [Linear model](../../sem2/model/models/linear.py) | Retain `SEM2Linear.coef_matrix()`, `mean_vector()`, and `cov_matrix()` and establish reliable fitting/reference tests. |
| [Base](../../sem2/model/models/base.py) and [discrete models](../../sem2/model/models/discrete.py) | Maintain `SEM2` and `SEM2Discrete.sample()`; consolidate discrete fitting and the existing partial-identification workflow. Add a simple guard against infeasible finite-state enumeration. |
| Data and [variable support](../../sem2/model/components/nodes.py) | Add the minimal mapping and conversion helper. Decide where support information belongs relative to `RandomVariable` before changing the interfaces (F12). |
| [Objectives](../../sem2/operators/scalar_operators.py) and [linear likelihood](../../sem2/operators/linear.py) | Use `LogLikelihood.evaluate()` and repair `EnergyLoss.evaluate()`, including named selection and sample/feature axes. Reuse `SEM2Loss` composition for query-specific fitting. |
| [Trainer](../../sem2/sem2trainer.py) | Consolidate `SEM2Trainer.train()` into one minimal trainer with loss and gradient-magnitude histories that users can inspect and plot. |
| [Interventions](../../sem2/operators/vector_operators.py) and [queries](../../sem2/operators/scalar_operators.py) | Build on `SEM2.sample(..., set_nodes=...)` and `PotentialOutcome`, `MeanPotentialOutcome`, and `ATE` evaluation. Remove global treatment/outcome coupling and support multiple treatment names. |
| Graphical identification | Add DAG-to-ADMG projection onto the observed variables and the ID algorithm for one observational margin (F33). An ADMG is an acyclic directed mixed graph. Keep the result format small and distinguish unsupported inputs from non-identification. |

The ID check concerns the supported graphical problem; it does not establish identification from extra parametric/proxy assumptions. Data fusion and latent-variable targets are outside its v0.1 scope. The numerical experiment checking whether lower/upper estimates coincide is deferred.

### Unit tests

Keep these in [tests/](../../tests/), separate from the four example-level acceptance cases:

- Named data mapping, explicit categorical conversion, tensor shapes, loss values/gradients, and basic trainer diagnostics.
- Finite-state probability calculations and the enumeration guard.
- Intervention equation replacement, unaffected mechanisms, renamed nodes, and multiple treatment names.
- Graph projection and ID results on reviewed reference graphs, including unsupported-input handling.

Regression tests must run independently of documentation notebooks. Shared example-generating code is fine.

Discuss each task in a focused Slack thread, then deliver the agreed changes in reviewed PRs. Agents can prepare examples and alternatives immediately; humans approve scientific assumptions, interfaces, and acceptance criteria before the affected implementation.

Review dependencies and proposed cleanup/deletions. | Build the chosen docs, consolidate the three notebooks, extract independent tests, separate runtime/test/demo dependencies, reconcile dependency files, and check obsolete `.gitmodules` use before removal. |

Start with task 1 and the reference-case choices for tasks 2–4. Documentation previews and the cleanup inventory can proceed in parallel. Each implementation PR should contain executed test results and a human reviewer; this plan does not assign contributors or authorize merges.

Keep three explanatory notebooks together under `docs/`: linear SEM versus lavaan, confounder adjustment, and discrete-IV partial identification. Cover the two-stage experiment with an executable Python example and tests; it does not require a fourth notebook.

## Completion and limits

v0.1 is ready for review when the package installs with separated dependencies, all four examples and the relevant unit tests pass on CPU at agreed tolerances, the documentation builds, and the retained notebooks run. Users must be able to inspect fitting diagnostics and understand the assumptions behind query results. Human acceptance of the milestone is separate from a public release.

Beyond the stated richer dataset schema, v0.1 excludes broad preprocessing, vector-valued nodes, new discrepancy families, robust multistart/continuation machinery, general uncertainty quantification, proximal/RDD examples, graph discovery, and GPU/HPC infrastructure. The decision record retains their individual priorities; this plan does not require a new CI pipeline or release process.
