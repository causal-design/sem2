This is the product scope and decision record, moved from `docs/plan/v0.1.md` after the September 17 review. The [implementation plan](../v0.1.md) now occupies that path and specifies ordered, separately reviewed units, file/function changes, and pseudocode. This specification does not prescribe a new class hierarchy.

**September 17 decisions:** implementation steps 1–5 are preparatory, with particular scrutiny of unnecessary new classes and methods; step 6 (the trainer) requires a separate technical review. v0.1 uses scalar variables. Categorical labels `0, 1, 2` are not formally the same as quantitative values `0, 1, 2`; deliberate conversion is separate preprocessing before training. The examples are PoliticalDemocracy and a Kang–Schafer adaptation targeting the average treatment effect on the treated (ATT), not a separate missing-data case study. The binary two-stage and discrete-IV requirements remain in place.

Review draft. Build a small, usable package for fitting structural equation models and asking causal questions under a supplied graph. v0.1 should support the four model/example families below through consistent interfaces, with tests and documentation that make their assumptions clear.

## Supported models and example-level acceptance

| Model/example family | What v0.1 must demonstrate |
|---|---|
| Linear Gaussian SEM | Use PoliticalDemocracy for the measurement/structural model example. Reuse the existing data and test; review latent-scale identification and residual-covariance representation against lavaan. Check implied moments and comparable coefficients, with a small known-model/OLS check where appropriate. Real-data estimates are reference fits, not known causal truth. |
| Discrete IV | Fit small finite-discrete IV models, including a ternary-treatment contrast. Apply strict instrument-level eligibility; compare numerical search endpoints against test-only LP/Balke–Pearl references for the same observed table and assumptions. Report numerical accuracy for manual review, without a predeclared bound-recovery threshold. Integrate the supplied extrapolation work through a native sweep and postprocessor; only automatic window-selection details await agreement. |
| Confounder adjustment: Kang–Schafer ATT | Adapt the simulation in [Kang–Schafer, section 1.4](https://arxiv.org/pdf/0804.2958) to a fully observed factual-outcome treatment problem, using the continuous energy-loss route. Target the average treatment effect on the factually treated, not the population ATE. Specify the potential-outcome generator, observed covariates, treated-population averaging and independent reference before implementation. No separate missing-data case study or new missing-data engine. |
| Two-stage sequential randomized experiment | Use the [agreed binary example](causal-query-interface-and-two-stage-example.md#agreed-two-stage-example): A1 is independently randomized, A2 is randomized conditional on intermediate L, and latent U confounds L and Y. Compare fixed joint regimes (1,1) versus (0,0), with population reference 0.46; also check (1,1) versus (1,0), reference 0.30. Verify known-model evaluation separately from observed-data fit recovery. |

Use a small CPU-run collection, not a large simulation grid. Humans review the reference cases and numerical tolerances where applicable; discrete-IV bound-recovery accuracy is diagnostic rather than a predeclared pass/fail threshold in v0.1. These examples cover F15/F16/F25/F32/F34/F35/F40/F44 in the decision record.

## User workflow and data handling

- For ordinary fitting, specify the model and named data, choose the objective and epoch budget, and call `fit`; the package owns the loop. Return inspectable loss/gradient history with an optional training-loss plot, keeping gradient detail out of the default plot. Then sample or evaluate named treatment/outcome queries without refitting solely to change the query.
- For causal queries, use the [agreed operator interface](causal-query-interface-and-two-stage-example.md#agreed-interface): one named scalar outcome, named fixed-value intervention dictionaries, explicit alternative-minus-reference direction, and `(value, info)` with a differentiable scalar tensor and small numerical/target details. These public query dictionaries are validated and converted at the query boundary; internal sampler interventions use `NamedBatch`. Rejecting legacy dictionary inputs at that low-level boundary does not reject the agreed query constructors. Omitted nodes follow their equations; numerical evaluation settings are separate from training configuration. Do not silently average category codes or launch fitting, identification, or a bound search. Dynamic-policy queries and a general query language are deferred.
- The Kang–Schafer example adds the specific ATT target: average the treatment-versus-control potential-outcome difference in the factually treated population. Ordinary ATE evaluation remains population-wide. Review the smallest example-level estimator or operator extension needed; do not obtain ATT by changing only its label, by conditioning on an already intervened treatment, or by fitting treated rows alone. This does not approve a general conditioning/counterfactual API or empirical-distribution framework.
- Check graphical identification within the agreed single-margin scope. On success, skip a bound search by default; estimation may still need fitting. On non-identification, warn and suggest an explicitly requested, query-specific numerical search. Unsupported inputs are errors, not non-identification results.
- For partial identification, specify the target before optimizing its signed contribution alongside observational fit. Report numerical lower/upper search estimates and separate fit diagnostics, not automatically sharp bounds or confidence intervals. Run only user-supplied penalties, using fresh starts by default or an explicit warm-start option, and pass native results to a separate automatic contiguous-window postprocessor. Regress ATE on signed penalty toward zero, separately for positive/lower and negative/upper searches. No generated grids, ordinary-use selector tuning, CSV compatibility adapters, or resumability are required; ordinary query evaluation must not silently start training.

Follow the [agreed minimal model–data handoff](minimal-model-data-interface.md) for F02/F03: require user-supplied pandas DataFrames (reject other input types clearly; no automatic format conversion), direct column/model name matching, automatic internal preparation, dataset-relative observation status, and complete cases with explicit reporting. `fit` is a convenience layer over one canonical Trainer, not a separate training engine. The handoff also records estimated intercepts by default, numeric constants fixing their values (`0` means no intercept), and correctness fixes to the existing parser expansion. Implement the richer dataset schema in v0.2; advanced missing-data handling is deferred until after v0.2.

Retain both finite-discrete fitting through `SEM2Discrete` and deliberate numeric treatment through base `SEM2`. Categorical-to-numeric conversion is a separate preprocessing operation before the data are ready for training. The small F28 helper, if supplied by SEM2, belongs at that boundary and is not automatically called by `fit`. Internal category encoding does not assign quantitative scores, and scoring does not itself switch model engines. Review the helper's name, placement, explicit mapping, and provenance contract without building the general preprocessing framework deferred under F09.

v0.1 fitting and examples use scalar variables, including scalar categorical variables with multiple levels. Do not add vector-valued DataFrame cells or a multi-column binding interface. Preserve existing low-level vector behavior only where necessary to avoid unrelated regressions; it is not a supported v0.1 example requirement.

Across the package, retain original categorical status, labels, and mappings after both internal encoding and deliberate categorical-to-numerical conversion. Record any user-supplied numerical interpretation. Do not silently use category codes as numerical outcome values for ATE: warn and suggest a distributional estimand or deliberate numerical conversion when that interpretation is absent. Let users choose treatment levels and contrast direction, such as ATE for `2` versus `0`, in ordinary queries as well as numerical searches. These are general requirements, not IV-specific features; see the [general variable and estimand decisions](identification-and-partial-identification.md#general-design-requirements-for-variables-and-estimands).

For discrete-IV fitting specifically, require at least two retained complete-case observations per declared instrument level; otherwise stop before fitting and warn with the counts. Do not silently drop/merge levels or add pseudo-counts. Validate full-data eligibility separately from minibatch safety.

The ID check concerns the supported graphical problem; it does not establish identification from extra parametric/proxy assumptions. Data fusion and latent-variable targets are outside its v0.1 scope. State the checked interventional distribution: its non-identification does not automatically prove every scalar functional nonidentified. The numerical experiment checking whether lower/upper estimates coincide is deferred; coincident numerical estimates are not an identification proof.

### Unit tests

Keep these in [tests/](../../../tests/), separate from the four example-level acceptance cases:

- Named data mapping, retention of category meaning after internal and explicit numerical conversion, tensor shapes, loss values/gradients, and basic trainer diagnostics.
- Finite-state probability calculations and the enumeration guard.
- Intervention equation replacement, unaffected mechanisms, renamed nodes, multiple treatment names, and user-selected contrasts such as `2` versus `0`, including a non-IV example. Follow the [query acceptance checks](causal-query-interface-and-two-stage-example.md#implementation-and-acceptance-checks): validate states before coercion, preserve mechanism parent order and appropriate dtype/device, regenerate intermediates, and retain probability normalization, gradients, and unchanged fitted parameters during ordinary querying.
- Graph projection and ID results on reviewed reference graphs, including unsupported-input handling.

For F34/F35, keep a few focused binary/non-binary IV checks, including a ternary-treatment contrast, category-provenance warnings, and absent/singleton instrument levels. Use independent LP/Balke–Pearl calculations only in tests under standard IV assumptions without silently adding monotonicity or linearity. Keep the observational loss separate from the signed estimand term in diagnostics, and report counts, total variation, and largest cell-probability error to users. Cover both initialization modes and the native sweep/postprocessor boundary. After selector agreement, check chosen points and intercepts on a small clean/flat/bent-end/weak-input set. Numerical recovery/stability is reviewed manually, not against a new v0.1 accuracy threshold; see the handoff for the exact interpretation limits.

Regression tests must run independently of documentation notebooks. Shared example-generating code is fine.

## Next steps and review decisions

The original agenda numbers below are retained for traceability, with September 17 decisions marked explicitly. Remaining options are not approved defaults. Steps 1–5 of the [implementation plan](../v0.1.md) are preparatory, not permission to invent abstractions. Step 6 has its own technical review before implementation; see the [trainer decision list](minimum-fitting-interface-and-diagnostics.md#step-6-technical-review-before-implementation).

Do not reopen the agreed DataFrame/name-matching and complete-case rules, node-owned support, named-record migration, package-owned trainer and diagnostics, Option B query interface, binary two-stage example, single-margin ID contract, or native penalty sweep. Fresh starts remain the default, warm starts remain optional, and automatic contiguous-window selection remains the chosen method family. Removing hard-coded names, fixing parser/intervention bugs, and implementing those contracts are work to do, not new design choices.

1. **Settled distinction; declaration details remain.** Categorical labels `0, 1, 2` and quantitative values `0, 1, 2` are different variables. Deliberate conversion precedes training; `fit` must not choose scores. Specify only the small representation/declaration contract needed to carry that supplied meaning and provenance. See the [preprocessing boundary](named-data-batches.md#discussion-ambiguous-numeric-columns).

2. **How should separate categorical-to-numeric preprocessing work?** Its separation from training is settled. Review the minimal explicit score mapping, unknown/missing-label handling, and retained original labels and scores. Do not introduce ordering-based automatic scores through preparation. The proposed helper is a small independent preprocessing unit, not a prerequisite for redesigning the trainer and not a user-authored column-to-model binding.

3. **What happens when a mean/ATE is requested for an unscored categorical outcome?** The warning and suggestion of deliberate scoring or category-probability contrasts are settled, but the query handoff promises a scalar result without specifying the failure behavior here. Decide whether to raise after the warning or use an explicit unavailable-result contract. Also clarify whether a category-probability contrast is only suggested for later work or supported in v0.1 through an explicit event-indicator score; do not silently add a new query family or return a mean of arbitrary codes.

4. **Which continuous energy objective and finite-sample estimator should be implemented?** Approve the loss formula, exponent/distance convention, normalization, and paired-versus-all-pairs cross term before repair. State the observation and model-draw sample axes separately and how self-pairs are handled. The current code is an implementation starting point, not evidence that its formula is the agreed objective. Preserve the agreed small trainer; this is not a choice of a new discrepancy family.

5. **What distance should discrete fitting use for categories without numerical scores?** The named-data plan separates labels from codes, while the current discrete loss measures Euclidean distances between stored states. Decide whether fitting requires deliberate scores or uses a specified category-based distance, and how variable scales enter the loss. Define when recoding labels should leave fitting unchanged; retaining provenance alone does not establish that invariance. This is a consistency gap between representation and numerical meaning, not permission to treat codes as scores.

6. **How should the IV fitting objective weight instrument levels and form valid batches?** Confirm whether to retain the current observed-frequency weighting across conditional margins, and specify a batching rule that respects the estimator—for example full-data evaluation or suitably formed batches. Full-data eligibility is already fixed at two retained observations per declared level; passing it does not make arbitrary minibatches valid. Do not silently drop levels, merge categories, or introduce pseudo-counts. Record the normalization used by the signed-penalty objective and final fit diagnostics.

7. **Settled: v0.1 uses scalar variables only.** No vector-cell or multi-column binding interface. Preserving existing internal widths to avoid regressions is not approval of vector-valued fitting in v0.1; a scalar discrete variable may still have several categories.

8. **Settled example: PoliticalDemocracy.** Adapt the existing dataset and test instead of introducing another measurement example. Review constraints, residual covariances and scale-aligned lavaan comparisons during the example's implementation review. Equivalent latent parameterizations must not fail merely for differing raw coefficients. Retain a small analytical/OLS check separately.

9. **Settled family and target: Kang–Schafer adapted to ATT.** No separate missing-data case study. Before implementation specify the factual treatment assignment, both potential-outcome mechanisms, observed versus generator-only covariates, treated-population averaging, overlap/adjustment assumptions, and independent ATT reference. Prefer a case that distinguishes ATT from ATE; constant-effect agreement alone cannot test the conditioning. Preserve covariate dependence. These are adaptation details, not permission to add a general empirical-distribution or counterfactual framework.

10. **Which concrete IV probability tables and numerical settings should accompany implementation review?** Select the small binary/nonbinary fixtures, including the ternary-treatment contrast, and record example penalties and numerical outcome scores. Match every test-only LP/Balke–Pearl reference to the same observed table and standard IV assumptions. This fills in test fixtures, not a reopened choice of IV assumptions, initialization modes, or search backend. Bound-recovery errors remain for manual review; do not add an accuracy threshold.

11. **What numerical acceptance settings should the non-IV fitting examples use?** Agree sample sizes, epoch/simulation budgets, seeds, and tolerances for the chosen linear/confounder cases and the already-fixed two-stage generator. Separate exact or known-model checks from finite-data fit recovery and Monte Carlo variation. These are implementation-review details; the two-stage graph, regime means, and contrasts are not open choices, and the IV diagnostic-only policy is unchanged.

12. **Which penalty points and windows are eligible for automatic extrapolation?** Set the minimum number of distinct penalties, treatment of zero and duplicates, and handling of failed or warned fits. Decide whether a window may span an omitted failed run and when two-point fallback is allowed. Consecutive-window search and separate positive/lower and negative/upper paths are settled. The [selector discussion](identification-and-partial-identification.md#open-questions-selector-details) contains recommendations, not approved rules.

13. **What counts as a sufficiently straight window?** Choose the prediction-error criterion, how to estimate a common scatter scale on each side, numerical safeguards for flat/nearly noiseless data, and acceptable/comparable-error cutoffs. Leave-one-out error with a scale from local triples is a proposal. Do not require ordinary users to tune these thresholds or present them as significance tests.

14. **How should acceptable windows be ranked?** Decide how fit quality, proximity to zero, and the amount of supporting data compete, including the comparison band and final tie-breakers. The agreed preference for proximity applies among adequately supported, comparably good windows; it does not authorize always selecting the nearest or farthest points.

15. **Which warnings and fallback estimate should be returned when selection is unreliable?** Agree stability checks and thresholds, including changes after removing a boundary point, distant narrow windows, and crossed endpoints. Specify fallback ordering when no window passes or no quality score is available. The existing rule still governs: warn for a computable but unreliable endpoint; mark an uncomputable one unavailable. Do not silently swap crossed endpoints or call one endpoint a complete interval.

16. **What must accompany each extrapolated endpoint?** Agree the minimum selected-point, fitted-line, quality, sensitivity, warning, and selection/unavailability information. Keep lower and upper paths separate and distinguish their fit diagnostics from the extrapolated value, which has no newly fitted distribution attached. This small postprocessor record need not be the same as an ordinary query's `(value, info)` result.

17. **Which documentation format and build/hosting approach should be used?** Choose using the requested two alternatives and one class/module preview. If those previews are not ready, assign their preparation rather than treating a platform as approved. Keep the three explanatory notebooks under `docs/`: linear SEM versus lavaan, confounder adjustment, and discrete-IV partial identification. Regression tests remain independent Python tests; the two-stage case needs an executable Python example, not a fourth notebook.

18. **Should the static graph-plot helper be included?** Judge a small labeled preview for usefulness and whether it distinguishes supplied latent causes from compiler-generated helpers. Include it only after that review; this is not approval of an interactive editor or graph discovery.

19. **How should the new dependencies be packaged?** Confirm where pandas, optional plotting/documentation tools, and test-only reference solvers belong, and how `pyproject.toml` and `requirements.txt` will agree. Separating runtime, test, and demo dependencies—and removing `pytest` from mandatory runtime requirements—is already settled. Decide the dependency arrangement, not whether to build new CI or a release pipeline.

20. **Which legacy artifacts may be removed after useful material is retained?** Review an explicit inventory of existing notebooks and stale files, identify sources for the three retained notebooks, and authorize any deletions individually. Verify the obsolete `.gitmodules` entry's use before removal. Notebook consolidation is agreed; neither this agenda nor a filename alone authorizes deletion.

Record decisions against this list and update the affected handoffs before their implementation. Keep exact import/keyword spellings and routine numerical defaults in bounded implementation reviews unless they change the agreed behavior. Each implementation PR needs executed checks and human review. Identification/search implementation remains paused pending its team discussion and a fresh request; existing approval requirements still apply. This planning update assigns no contributors and authorizes no implementation, merge, or release.

## Completion and limits

v0.1 is ready for review when the package installs with separated dependencies, all four examples and the relevant correctness tests run successfully on CPU, numerical checks meet their agreed review criteria, the documentation builds, and the retained notebooks run. Discrete-IV bound-recovery accuracy remains a manual diagnostic, not a predeclared tolerance gate. The detailed automatic selector must be agreed, implemented, and exercised before claiming completion; the supplied experimental function and this documentation do not establish that outcome. Users must be able to inspect fitting diagnostics and understand the assumptions behind query results. Human acceptance of the milestone is separate from a public release.

Beyond the stated richer dataset schema, v0.1 excludes broad preprocessing, a new general vector-valued-node framework, new discrepancy families, robust multistart/continuation machinery, general uncertainty quantification, proximal/RDD examples, graph discovery, and GPU/HPC infrastructure. Preserving existing vector widths during the named-data migration does not expand that scope. The decision record retains their individual priorities; this plan does not require a new CI pipeline or release process.

Validation-loss monitoring, automatic stopping/best-iterate restoration, estimator-specific cross-fitting, and public **trainer-loop** `step`/`evaluate` primitives are [possible future extensions](minimum-fitting-interface-and-diagnostics.md#possible-future-extensions--unscheduled), not commitments to a particular release. This deferral does not apply to the agreed query/operator `.evaluate()` interface or the required final loss evaluation. Keep the v0.1 trainer small; do not make these extensions milestone prerequisites.
