## Purpose

The group also considered how to evaluate the method, when to add confidence intervals, and how to use coding agents without losing control of the software architecture.

## RHC application

### 1. Data preparation

Chiara downloaded a dataset with more than 5,000 patients and prepared a simple confounder-adjustment example with a binary treatment and binary 30-day mortality outcome. The preprocessing included:

- separating treatment, outcome, and candidate confounders;
- one-hot encoding categorical variables;
- retaining continuous and binary indicator variables, for about 65 covariate columns after encoding; and
- filling missing numeric values with column means.

This work exposed an important usability problem: users currently have to perform categorical conversion, missing-value handling, and column organization themselves. The package does not yet provide a data layer that records variable types, transformations, or named mappings from table columns to model nodes.

### 2. The proposed graph does not preserve the covariate distribution

The initial graph made every covariate a parent of both treatment and outcome, with no edges among the covariates. In the current scalar-node representation, this makes the fitted model generate the covariates independently. Because the real covariates are generally dependent, resampling from that model changes their joint distribution and therefore changes the population over which an average treatment effect would be computed.

The group agreed that this is a limitation of the current package rather than an error by the user. A more appropriate design would treat the complete covariate vector as one multidimensional object whose joint distribution can be preserved. For an ordinary adjustment problem, estimating a flexible high-dimensional generative model for the covariates may be unnecessary: the empirical distribution of the observed covariate rows is often sufficient.

One possible implementation is a multidimensional exogenous node with a supplied distribution, including an empirical distribution over the observed covariate rows. SEM2 does not currently support that feature. Adding a scalar latent parent to every covariate is expressible in principle, but would still require learning a difficult high-dimensional generator and was not considered an attractive solution for this use case.

### 3. Near-term evaluation

The full RHC problem is too high-dimensional for a useful test of the current package. As a short-term smoke test, Chiara can retain one or two covariates, specify a small graph, and check that the fitting and intervention pipeline runs. Any resulting number should be treated only as an algorithmic demonstration, not as a credible effect estimate for the full RHC problem.

Controlled simulations are the preferred way to study whether the fitting method recovers known targets. The group also identified a low-dimensional proximal-proxy graph as another possible example with a fixed graph and existing theory.

## Point estimates and uncertainty

The package should first make point estimation reliable for simple designs. General confidence intervals require additional statistical assumptions and theory, and are difficult to assess before the underlying fitting procedure can be tested in simulations and applications.

The discussion mentioned bootstrap-like, jackknife-like, and influence-function approaches as possible computational routes. These remain future work. The immediate priority is a polished workflow that fits simple models, reports point estimates, and can be evaluated against known answers before a general confidence-interval interface is added.

## AI-assisted development workflow

Qingyuan proposed using coding agents more extensively to accelerate development. The group supported trying this approach, subject to feedback from Max and Amruth and to a disciplined review process.

The main risk is not that an agent cannot produce working code, but that it may produce code that is misaligned with the research design, unnecessarily complex, or poorly integrated with the existing architecture. The proposed safeguards are:

- write down the desired behavior and important design decisions before implementation;
- maintain a clear inventory of requested features and known issues;
- preserve and explicitly review the package architecture;
- ask an agent to produce an implementation plan before writing code;
- use strong behavioral tests and realistic examples to check alignment;
- review changes through branches and pull requests rather than accepting large code changes directly; and
- have several contributors question unexpected abstractions, files, or behavior.

The repository documents have distinct roles in this process: `README.md` provides stable human-facing context, `PROJECT.md` records the current state and next steps, and `AGENTS.md` gives coding agents durable repository guidance. Documentation and tests are part of the control system for agent-written code, not an afterthought.

The proposed first planning exercise is to collect the desired features and problems already recorded in GitHub issues, meeting transcripts, reviews, and repository documents. The team can then remove bad or unnecessary ideas, prioritize the remainder, check whether the current architecture can accommodate them, and implement bounded changes one at a time.

## Decisions and working direction

- Do not use the current independent-covariate graph as a substantive analysis of the full RHC dataset.
- Use a one- or two-covariate RHC example only as a pipeline smoke test, with its limitations stated explicitly.
- Use controlled simulations to evaluate statistical performance against known answers.
- Explore support for a multidimensional exogenous covariate node with a supplied empirical distribution, rather than forcing users to estimate an unnecessary high-dimensional covariate generator.
- Consider the proximal-proxy graph as a second low-dimensional test case.
- Prioritize reliable point estimation for simple designs before implementing a general confidence-interval interface.
- Try a more AI-assisted development process, provided that architecture, specifications, tests, and human review remain under explicit team control.
- Start by consolidating and prioritizing the existing feature requests and known issues; do not ask an agent to redesign or expand the package without an agreed plan.

## Questions to carry forward

- What is the smallest data abstraction that can handle categorical encoding, missing values, named columns, and multidimensional covariates without becoming application-specific?
- Should an empirical covariate distribution be represented as an exogenous node, a dataset-level sampling mechanism, or another reusable component?
- Which simulated designs best test recovery of point estimates under continuous, discrete, and proxy-variable graphs?
- What evidence should be required before a point-estimation workflow is considered reliable enough to support confidence intervals?
- Which feature requests are essential to the near-term package, and which should remain research experiments or be dropped?
- What branch, review, testing, and documentation rules will keep agent-written changes understandable and aligned with the agreed architecture?
